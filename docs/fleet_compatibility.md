# Transportation Order compatibility shim and Shipment demo

## Finding and scope

Fleet commit `8dd035a` has a Transportation Order controller and client script
that require `assign_transport`, but its DocType JSON and the inspected
`tms.localhost` metadata lack that field. The repository is shallow and has one
local commit. No local history proves whether this was a removed standard field,
a missing exported Custom Field, or an omitted migration. The defensible diagnosis
is a shipped schema/controller mismatch, with legacy assignment code coexisting
with the newer Manifest/Trips workflow; a Frappe v16 regression is not established.
There is no active Fleet fixture/install hook restoring the field.

The existing `Transport Assignments` JSON is explicit (`istable: 1`), and Fleet's
`assign_vehicle` constructs that DocType with `parentfield: assign_transport`.
Its Python controller is an empty Document subclass. No replacement child DocType
is needed. `Cargo Detail` is another existing child table referenced by its `cargo`
Link and by the Order's `cargo` table; its controller is also empty. Cargo Detail
contains container, location, route, weight, billing, and Manifest references and
has mandatory operational fields. The basic demo leaves both child tables empty.

## Restored field

- Parent: Transportation Order
- Fieldname: `assign_transport` (exact name required by existing Fleet code)
- Fieldtype: Table
- Options: Transport Assignments
- Label: Assign Transport
- Insert after: `html1`
- Optional; no default rows, unique constraint, or validation override
- Custom Field module: Transport Management; system-generated by Frappe's API

`transport_management.fleet_compatibility.ensure_assignment_table` runs from
`after_migrate`. This source-controlled installer is used instead of a fixture
that might overwrite a site's existing field. It checks the child schema, reuses
an existing compatible standard/custom field, and raises on conflicts. It never
renames or edits Fleet fields. Run migrate after installing this app and after
updating its code. A future Fleet standard field with the same schema is reused;
a future incompatible schema requires review. Do not delete upstream/custom fields
automatically as part of an upgrade.

The helper calls Frappe's standard `create_custom_field` without ignore flags.
Initial installation must use normal migration: interactive metadata validation
also checks Fleet's unrelated legacy Link targets and fails on missing `Unit of
Measure`/`Files`. Frappe itself defers those metadata checks during migration; this
shim does not set `in_migrate`, `in_patch`, `in_fixtures`, `ignore_validate`, or
`ignore_links`. Fleet document validation still runs on every normal order save.

## Fleet behavior retained

`validate` copies Customer.default_currency to each assignment's `currency`, then
checks `assigned_vehicle` against Truck.status. For `In Trip`, it looks for a
`Vehicle Trips` record referencing the child row's doctype/name and throws if none
exists. `before_save` sets Waiting Assignment for an empty table; for Container it
compares `container_number` against cargo rows; for Loose Cargo it sums `amount`
and compares that total with the order's `amount`.

Persistence methods use `assign_transport` for referenced Import/Export orders,
including version-2 rows owned by the order. The demo uses standalone orders with
both reference fields blank and does not exercise those legacy paths.

Known upstream limitations left intact:

- Truck offers `On Trip`, whereas Order checks `In Trip`.
- `Vehicle Trips` does not exist on the inspected site; Trips is a different DocType.
- Order `unit` targets absent `Unit of Measure`; `file_number` targets absent `Files`.
- Assignment `units`, `file_number`, `import_reference`, and `export_reference`
  target absent Unit of Measure, Files, Import, and Export respectively.
- Assignment rows require route, service item, currency, and rate, with conditional
  vehicle/trailer/subcontractor fields. No dummy rows are inserted to satisfy code.
- Fleet's old Create Vehicle Trip button calls a legacy `vehicle_trips` method.

These limitations exclude assignment execution, invoicing, import/export, and
Trips from the basic demo. They do not require populating those optional fields
on an empty standalone order. The shim makes no claim to repair all Fleet workflows.

## Shipment behavior

Quantity must be finite and greater than zero; loading and offloading sites must
be different. A valid order with a customer is required. A missing Shipment
customer is fetched; a supplied conflicting customer is rejected server-side.
`fetch_if_empty` preserves supplied values until the server can check them. The
form clears/re-fetches Customer when its order changes, guarding stale responses.

All existing links, reference fields, SHP naming, lifecycle/status behavior, and
optional Trip remain. No historical fields or Trips are created. Shipment UOM
continues to use ERPNext UOM; do not copy the Order's legacy unit into it.

## Commands

From `/workspace/development/frappe-bench`:

```sh
bench --site tms.localhost migrate
bench --site tms.localhost clear-cache
```

Reload Desk in the browser after migration. For another site substitute its name.
The compatibility helper can be rerun after migration to verify reuse:

```sh
bench --site tms.localhost execute transport_management.fleet_compatibility.ensure_assignment_table
```

Run targeted tests on a test/demo site (CI=1 enables tests for that command only):

```sh
CI=1 bench --site tms.localhost run-tests --module transport_management.tests.test_fleet_compatibility
CI=1 bench --site tms.localhost run-tests --module transport_management.transport_management.doctype.transport_shipment.test_transport_shipment
```

Tests use standard unittest cases under Frappe's site runner, avoiding automatic
Fleet test-record generation. The normal order insert/reload/save test rolls back
to its savepoint. Nonempty assignment tests invoke the unchanged Fleet controller
on unsaved rows and mock database lookups; they are not proof that Fleet's old
trip/invoice execution works. Shipment tests cover the custom controller separately.

For the UI demo, create a standalone Transportation Order with a Customer and Date,
leave Cargo/Assign Transport empty, and leave legacy Unit/File/Request Origin blank.
Save it. Create multiple Transport Shipments selecting that order, enter each
load's quantity/UOM, sites, material, vehicle/driver and references, then save as
drafts with Trip blank. Shipment totals do not update Fleet assignment totals.

No permanent business demo masters or shipments are created by this compatibility
migration. The separately invoked setup from the original demo request is:

```sh
bench --site tms.localhost execute transport_management.demo.setup_demo_data
CI=1 bench --site tms.localhost run-tests --module transport_management.tests.test_demo
```

It creates/reuses the named customer, two locations, aggregate material, Fuel UOM
Litre, UMAIR, truck 29413-FUJ, and one standalone 80.8 order. Locations assume
United Arab Emirates; a missing Country, duplicate natural keys, inactive driver,
disabled Fuel UOM, or unavailable truck stops setup without overwriting records.
The truck's unknown technical values are marked DEMO; its timeline comment also
labels numeric acquisition year 2000 and fuel choice Diesel as placeholders.
Driver cellphone DEMO-UMAIR is a Data placeholder, not a real telephone number.
No accounting Company or shipment UOM is guessed. Normal document validation and
permissions apply. Run setup serially; leave the order's special-instruction demo
marker intact so subsequent executions reuse it. Repeated runs do not update
existing masters. Setup rolls back its business inserts on failure.

The end-to-end test runs setup twice and saves/reloads two distinct shipments
against one order, checking customer fetching and naming. It rolls all test
business records back to a savepoint; its temporary UOM is only for the test.

## Complete assign_transport usage inventory

An entire-repository `rg -n 'assign_transport' apps/vsd_fleet_ms` search found only
the Transportation Order Python and JavaScript files. No other Python/JavaScript
file or exported metadata defines it. Line numbers refer to inspected Fleet commit
`8dd035a`.

Python (`transportation_order.py`):

- 20, 22: currency propagation and vehicle validation loops.
- 41, 45, 55: empty/container/loose-cargo assignment status.
- 66, 84: child retrieval and persistence for referenced requests.
- 97: commented-out parent-setting code (inactive).
- 146, 148, 150, 156: load referenced/own assignment rows, including version 2.
- 304: `assign_vehicle` creates Transport Assignments with this parentfield.
- 370: invoice creation updates assignment invoice links and legacy vehicle trips.

JavaScript (`transportation_order.js`):

- 6–8, 46–48: require assignment grid, disallow direct additions, hide removal.
- 10: render Assign Vehicles button calling `cur_frm.cscript.assign_transport`.
- 64: service-item query for assignment rows.
- 80: repair container/cargo associations.
- 105: assignment grid row access (mostly commented legacy display logic follows).
- 190, 193: loose-cargo assigned totals.
- 207, 209: select assignment rows to invoice.
- 248, 254, 260: prevent processed-row removal/container additions; set loose defaults.
- 422: passes `doc.assign_transport` to legacy vehicle-trip API.
- 441, 449, 455, 462: assign selected cargo, detect existing container rows,
  append Transport Assignments and refresh the table.

The same JavaScript registers Transport Assignments handlers for row rendering,
amount/date/transporter/vehicle/trailer/driver/route changes and legacy trip creation.
Those access child fields whose complete shipped schema is below. Some legacy
handler accesses (e.g. `assigned_idx`, `cargo_idx`, `section_extra`, `driver_licence`)
are transient arguments or stale UI references, not reasons to invent schema.
